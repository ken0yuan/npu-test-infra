# 已知边界与验证状态

- 目标是 API 与测试的观测关系；不是 C++ dispatcher、NPU 内核或闭源算子的调用链。
- 仅 Linux + CPython 3.11；C 适配器在本机编译，没有 x86 指令或固定 PyTorch 源码地址。ARM64/昇腾尚待实机验证。
- 已有 PyTorch 测试能在 NPU 执行，是宿主环境的前提；插件不会转换硬编码 CUDA 测试。
- torch_npu 如果替换 torch 上的 Python callable，注册表按实际对象重新解析；不支持的调用协议会留状态。原生符号、类实例化、属性读取不等同普通函数调用，不能宣称全部 10,362 个条目均可观测。
- 新线程、常见 subprocess/multiprocessing 和池任务有归属跟踪。无法接管的外部程序、已有非受控线程、强退未回执子进程等保留 gap；不能据此断言某个特定 API 必然遗漏。
- 0.1.1 已修复注册表并发刷新：在锁内构建独立副本，完整后发布；失败保留旧映射并记录 gap。用户代码在扫描期间重新绑定对象时，版本标记保持为待刷新，避免误认为已经同步。
- 0.1.1 使用原生 opcode trace 守护和 profile 多路转发，保住 cProfile / `_lsprof` 启停期间的 Python 可观测调用，并保留它们自己的事件与统计；已覆盖提前创建、提前启用、同一行启停、线程和异常用例。原有 Python trace 客户端也转发原事件。
- 任意原生扩展或绕过接口的代码如果同时破坏 trace 守护和 profile，仍不能保证完整采集；可观测到的绕过记录 gap，阶段边界检查状态。修复不是对所有第三方调试器、分析器和恶意绕过的全面兼容声明。
- opcode 守护会增加 Python 执行开销；尚未测量真实 PyTorch 全量测试或 ARM/NPU 上的性能，不能将小样本回归耗时当作性能保证。
- 0.1.1 已迁入 SQLite 热回滚日志恢复，只恢复所属 PID 已不存在的分片，保留原数据库/日志字节，先验证恢复副本，再恢复原件核对并重试合并。不会修复任意数据库损坏，也不能找回异常退出前未提交的数据；存活或复用 PID 一律保守拒绝恢复。
- 每个关系保留第一个调用位置；同对象别名不区分调用语句具体写了哪个名称；间接调用属于当前测试阶段，不代表测试断言针对该 API。
- 本版不支持 pytest-xdist、自动增量重跑、断点续采或跨运行自动合并。每次运行使用独立目录，保留完成与中断证据。
- 实例化阶段（pytest collection）的 API 调用没有独立测试实例归属；本版不把这些调用猜测分摊给各个测试。
- 测试失败不等于采集失败；采集完成不等于测试全部执行，也不等于全量无遗漏。跳过/未运行测试仍可能没有 call 阶段。
- 测试输出和返回码仍由 pytest 原样提供，插件数据库不以测试通过/失败为产品。

独立回归使用人工小台账和模拟 torch/torch_npu 命名空间，另有真实 x86 PyTorch/CUDA 小样本及上游测试对照；这不等价于真实昇腾算子验收。

pytest 结束钩子的汇总可能早于子进程最终落盘。0.1.2 提供进程退出后的 `settle` 重汇总；应查询新目录。它可以补入已落盘的迟到关系和回执，但无法恢复子进程未提交的调用；缺少完成回执、空分片仍保留为 gap。`capture_finished` 与 gap 数必须同时查看，不能把缺少回执直接认定为某个 API 已遗漏。
